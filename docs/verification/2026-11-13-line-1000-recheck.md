## Browser coverage

- Origins: map `/`, today `/air`, community `/community`, requests `/requests`, 250 paths each. Both settings-back/re-entry and close-to-origin are asserted where exercised.
- Viewports: 320px (252 paths), 375px (252), 390px (248), 430px (248). Horizontal overflow is checked after every completed action.
- GPS: valid (334 paths), permission denied (333), coarse accuracy (333), plus missing/ready/stale saved location fixtures.
- Actions: edit/cancel, edit/save, update/clear GPS, location help, settings back/re-entry, reload, LINE test, disconnect, create/copy/link code, PM2.5 toggle, quiet hours and maximum search radius.
- API cases include failed initial preference reads with recovery, failed saves, failed GPS persistence/deletion, failed LINE code creation/disconnect, and throttled test messages.
- Page JavaScript errors fail a path. Requests outside the local origin are blocked. LINE test/code/status operations are fixtures and never call LINE.
- A stable path ID reproduces action order and fixture conditions. Browser report: `output/playwright/line-mobile-routes-0-1000.json`. Separate timeout replays: `output/playwright/line-mobile-timeout-rechecks.json`.

## Issue found and fixed

After a manual GPS update/delete, `AlertLocationControls` incremented its request generation but the background location-refresh listener still compared results with the generation captured at initial mount. A later valid background refresh was silently discarded.

The listener now captures the current generation for each read and uses a separate read sequence so older reads cannot overwrite newer ones. A regression test performs a manual update, dispatches a subsequent background update, and confirms that the displayed readiness changes to the new server state. The browser matrix was restarted from path 0 on a rebuilt application after this fix.

## Timeout investigation

The initial run retained three timeouts: path 807 waited for the polled LINE linked state; paths 810 and 811 could not complete click actionability/stability checks on the save button within five seconds. The screenshot showed the save button rendered and enabled; no page exception was recorded. All three passed when replayed individually with identical application code, fixture conditions and timeout, including five additional rounds each.

This does not prove a specific environmental cause or justify reporting a clean 1,000/1,000 first pass. The initial result remains 997/1,000 with three transient timeouts; all 1,000 distinct paths have a passing result after explicit recheck. No timeout was hidden through automatic retries or forced clicks.

## Reproduce

```sh
.venv/bin/python -m pytest backend/tests/test_line_1000_cases.py backend/tests/test_line_worker_matrix.py -o addopts='' -q
node scripts/test-line-candidate-matrix.mjs
node scripts/test-line-delivery.mjs
```

For the browser harness, build/run the demo frontend on `127.0.0.1:3117` with the local API proxy to the demo backend on `:8017`. Open a `playwright-cli` session named `clearpath-1000`, then run:

```sh
.venv/bin/python scripts/check_line_mobile_routes.py --count 1000 --batch 24
.venv/bin/python scripts/check_line_mobile_routes.py --start 807 --count 1 --batch 1
```

Browser checks use real UI with fixture APIs. Live LINE behavior, production webhook latency/quotas, hosted RLS/advisors and deployment remain outside this local recheck. See [the activation runbook](../runbooks/line-nearest-pin.md).
