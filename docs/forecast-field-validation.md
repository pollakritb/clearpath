# CAMS forecast field validation

## Raw CAMS storage (active in ClearPath Production)

`/api/cron/cams-snapshots` is a separate authenticated collector. With `CAMS_SNAPSHOT_COLLECTION_ENABLED=true`, it requests five forecast days for valid Air4Thai station coordinates and stores up to 120 consecutive future hourly PM2.5 values per station in the existing private `forecast_provider_snapshots` table. It records each run in `forecast_provider_sync_runs`. Public forecasts now read the latest completed snapshot from this table. The collector does **not** write `forecast_runs`/`forecast_predictions` or generate a ClearPath model forecast. The run uses a six-hour due interval and keeps requested coordinates, returned grid coordinates, and actual retrieval time as metadata. Missing or invalid hours are not invented; a shorter provider horizon is shown as available. The collector prunes expired CAMS-only rows in bounded batches after a successful run; the default snapshot retention is seven days. Apply `20261027_allow_cams_snapshot_retention.sql` before increasing the collection horizon so DELETE can pass the forecast-reset trigger. This operational store is not the long-term field-validation dataset described below.

The Production Forecast Reset originally installed `block_forecast_writes_during_reset()` on 11 tables. It silently discarded inserts into both provider tables, yielding HTTP 201 with zero persisted rows. Migration `20261016_allow_raw_cams_evidence_during_forecast_reset.sql` was applied to the verified ClearPath project; it allows `openmeteo_cams` rows in those two tables while keeping all other forecast writes blocked. The backend now rejects empty provider write responses, and the workflow prints the returned status/count; a green HTTP request alone is not evidence of persistence.

On 2026-10-16 Production was configured with `CAMS_SNAPSHOT_COLLECTION_ENABLED=true`, `CAMS_SNAPSHOT_EXPECTED_SUPABASE_REF=qnrtryspglioqhdxglzu`, and the separately gated six-hour GitHub workflow enabled. The initial collection and six bounded scheduled batches succeeded for 177 stations with 24 hours each. A repeated workflow reported `not_due` for all six batches. Supabase contained 8,496 raw CAMS snapshot rows and seven successful runs, including station `103t`; `forecast_predictions` and `forecast_runs` remained empty. Keep `FORECAST_SYSTEM_PAUSED=true` and `FORECAST_VALIDATION_ENABLED=false`. Monitor the workflow, retention results, and database storage.

The code flag defaults to false outside the explicitly configured Production environment. The workflow makes six bounded `batch_index=0..5` requests, each covering roughly 30 stations with an independent six-hour due check, to stay below the Vercel request timeout. At 177 stations, four runs per day and at most 24 hours per station, budget for up to 16,992 new rows per day; partial provider responses yield fewer. The collector removes expired `openmeteo_cams` snapshots and run telemetry in bounded batches after each successful write, using the configured provider retention windows (defaults: 7 and 30 days); it never deletes another provider's rows. Monitor `forecast_provider_sync_runs`, `forecast_provider_snapshots`, workflow failures, and Supabase disk usage. To pause collection without changing the public forecast, set the GitHub variable `CLEARPATH_CAMS_SNAPSHOTS_PRODUCTION_ENABLED=false`; the server flag is a second independent kill switch.

The public forecast uses unadjusted Open-Meteo/CAMS Global PM2.5 for the requested station or area. It does not use Air4Thai readings to alter the forecast. The response carries the requested coordinates, provider grid-cell coordinates, UTC `fetched_at`, and per-point UTC `valid_at`. Clients render `valid_at` in the user's time zone. A 24-hour request returns consecutive future hourly slots only; a partial provider response is marked `external_provider_partial_horizon`, never filled with invented values.

The isolated `/api/cron/forecast-validation` collector is authenticated but **disabled by default** (`FORECAST_VALIDATION_ENABLED=false`) and is not registered with any Production scheduler. The migration `20261015_forecast_validation_evidence.sql` is not applied automatically. It creates private snapshot and reserved one-hour observation tables with no public RLS access. On a future six-hour schedule, the collector would choose station `103t` plus nine geographically spread stations, save the next 24 hourly provider values along with both coordinate pairs and timestamps, deduplicate by station/UTC collection slot/valid time, and retain at most 90 days. This is field-test evidence only; the public API never reads it. The observation table is intentionally empty until its source is verified.

Before enabling, verify the official Air4Thai **one-hour PM2.5** observation source, its averaging window and timestamp semantics, station mapping, completeness, data licence, and storage quota. The existing `pm25_readings`/Air4Thai headline value must **not** be treated as a one-hour truth set; it may be a rolling 24-hour value. Collect only explicitly labelled one-hour observations, align them to forecast `valid_at` in UTC, and reject forecasts fetched after the valid hour. The pure validation helpers can then report provisional MAE and signed bias for 1–6h and 7–24h, with sample count, missingness and station breakdown. Do not advertise accuracy, apply bias correction, or enable another model based on these provisional metrics alone. Field-test activation, migration application, and Production scheduling require a separate review.

Provider reference: [Open-Meteo Air Quality API](https://open-meteo.com/en/docs/air-quality-api). CAMS Global grid spacing is approximately 45 km; hourly API values do not imply hourly native model resolution or point-specific accuracy.

## Field diagnostics extension (staging-ready, not active in Production)

The map has a user-triggered coordinate inspector for a selected Air4Thai station, searched place, or rounded GPS position. It calls the existing public `/api/forecast` only. The circle is the requested point, the square is the Open-Meteo response grid-cell centre, and the dotted line is the Haversine distance between those points. Missing grid coordinates produce no invented marker or distance. This interaction **does not write validation snapshots**. The inspector separates `valid_at` (Thai local display) from `fetched_at` (retrieval time, not CAMS model issuance time) and labels measured versus forecast values.

`scripts/survey_cams_grid.py` performs one spatial survey and writes a timestamped CSV plus summary JSON under the gitignored `.forecast-validation/` folder. It requires `APP_ENVIRONMENT=staging`, distinct `STAGING_SUPABASE_URL`/`STAGING_SUPABASE_SERVICE_ROLE_KEY`, and an exact `--expected-ref`; a URL matching the local Production project is rejected. `--demo` exercises only local demo stations and is **not** an all-Air4Thai survey. Output is historical survey evidence, never a current forecast. Provider requests are batched and missing/failed stations are retained with reason codes. Do not put either credential in a command line, report, or log.

The existing six-hour `/api/cron/forecast-validation` endpoint remains behind `FORECAST_VALIDATION_ENABLED=false` and has no Production scheduler. Apply `20261015_forecast_validation_evidence.sql` then `20261015_forecast_validation_diagnostics.sql` to **ClearPath Staging only** before an opt-in staging test. The collector inserts snapshot rows with conflict-ignore: retries of one UTC slot cannot overwrite evidence, while later slots for the same station and valid hour remain separate. Per-slot telemetry records full/partial/provider-unavailable status and missing reasons. In Staging it fails closed unless `FORECAST_VALIDATION_COHORT_IDS` names exactly ten reviewed stations including `103t`. `scripts/select_cams_cohort.py` checks seven days of official Air4Thai `type=hr` history for **presence only**, then proposes a geographically spread cohort; its `--demo` mode is not an all-station survey. Review the generated gitignored `.forecast-validation/cams-cohort.json` before setting the IDs. Hourly timestamp semantics and reuse licence remain unverified, so this scan never inserts truth observations or calculates accuracy. The optional GitHub staging workflow is disabled unless the repository variable `CLEARPATH_FORECAST_VALIDATION_STAGING_ENABLED` is explicitly set to `true` and separate Staging URL/secret are configured; it is not a Production scheduler.

The private observation table is reserved for an independently verified Air4Thai one-hour adapter. The second migration adds `window_start_at`, `window_end_at`, and `timestamp_semantics_verified=false`. Pairing requires an explicitly verified `[start,end)` 60-minute window ending at `valid_at`, a forecast fetched before that hour, and a nonnegative value. No production or staging observation ingestion is enabled yet. [PCD explains that the Air4Thai headline is a 24-hour mean while the one-hour values appear separately](https://epo08.pcd.go.th/th/news/detail/180206); the catalogue's hourly listing has no explicit licence, so endpoint semantics and permitted use still require confirmation.

`scripts/evaluate_cams_accuracy.py` is staging-only and outputs private shadow metrics: raw CAMS count/MAE/signed bias/high-dust recall and precision (`>37.5 µg/m³` observed one-hour mean), split by station, broad coordinate region, and exact lead-time bands. It runs an 80/20 chronological test plus whole-station holdouts after at least 14 days of verified station-hours. Candidate station bias, nearby residual and persistence use only observations available before each snapshot's `fetched_at`; a station with no eligible nearby evidence gets raw CAMS only. Forecast snapshots for the same station/valid hour are all scored, but distinct station-hours are also counted. The one-hour mean and CAMS point-at-time differ in temporal definition; this limitation remains attached to results. No candidate feeds the public API. `FORECAST_VALIDATION_PUBLIC_METRICS_ENABLED=false` prevents public accuracy claims; even if enabled after review, a station requires at least 100 distinct verified hours spanning 14 days. Areas without a station continue to say “ยังไม่มีผลประเมิน”.

Next gate: confirm the official one-hour data interface, mapping, end-of-window semantics, completeness, and licence; implement a separate ingestion/matching job only after that evidence is recorded. Until then no MAE, Bias, calibration winner, or all-station spatial-survey numbers can be claimed from real observations.
