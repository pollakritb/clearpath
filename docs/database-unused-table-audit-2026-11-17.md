# ตรวจตารางที่อาจเลิกใช้ — ClearPath production 17 พฤศจิกายน 2569

ขอบเขต: อ่าน catalog, function bodies, dependencies, cron, สถิติ PostgreSQL, จำนวนแถวเฉพาะตารางเล็ก และ source ของ deployed commit `155fd3f` ไม่แก้ production ไม่ลบข้อมูล ไม่เรียก worker และไม่ deploy

## ข้อสรุป

- ไม่พบทางใช้งานธุรกิจปัจจุบันสำหรับ `public.report_reviews`; มี 0 แถว และไม่มี insert/update/delete ในสถิติที่เก็บอยู่ เป็นตัวเลือก retirement ที่ชัดที่สุด แต่ต้องถอด view/trigger/FK/identifier registry/เครื่องมือที่อ้างอิงให้ครบก่อน drop
- `community_device_evaluations` และ `community_evidence_outcomes` มี 0 แถว แต่ยังไม่ถูกถอดครบทั้งระบบ: deployed HEAD มี CLI `scripts/community_evidence.py` → `evaluation_ingest.py` → `ingest_community_evaluation`; SQL reconcile/trigger และการอ่านประวัติผลยังอยู่
- `activities` มี 0 แถว และไม่พบ UI production เรียก activities จาก hooks/components แต่ API `/api/community/activities` และตารางยังเชื่อมกัน เป็นฟีเจอร์ที่พิจารณา retire ได้ ไม่ใช่ตาราง orphan ที่ drop ได้ทันที
- `community_policy_release` ยังถูก `process_community_xp` อ่านโดยตรง แม้ control ปัจจุบันเป็น v1 และ launched_at=null; ห้ามลบเพียงเพราะ v2 ไม่ active
- CAMS snapshots/sync runs ยังมี production read/write paths; ตาราง snapshot มีภาระพื้นที่สูง แต่ยังไม่ใช่ตารางที่พิสูจน์ว่าเลิกใช้
- private aliases, XP/Trust ledger, retry queues และ Supabase-managed tables ไม่จัดเป็นตารางทิ้งจากการตรวจรอบนี้

## วิธีและข้อจำกัด

1. ใช้ source จาก Git HEAD ที่ตรงกับ deployment เพื่อหลีกเลี่ยงงาน cleanup ใน working tree ที่ยังไม่ deploy
2. แยกชื่อใน identifier registry, migration, test และ reset/preflight script ออกจาก business read/write
3. ตรวจ Python AST สำหรับ `.table(...)` และ `rpc(...)` พร้อมตรวจ SQL bodies, trigger, views, FK และ frontend Realtime subscription
4. ตรวจ cron โดยบันทึกเฉพาะชื่อ ตารางเวลา และชื่อฟังก์ชัน ไม่บันทึกคำสั่งที่อาจมี token
5. สถิติ database เริ่มรอบสะสมที่ 2026-10-31T02:44:35.738254+00:00; ตัวนับเป็นข้อมูลประกอบ ไม่ใช่หลักฐานว่าไม่มีผู้เรียกหรือว่า scan มาจากผู้ใช้จริง สถิติราย relation อาจถูก reset/เปลี่ยนจาก DDL ได้
6. ไม่มี runtime tracing ครบทุกเส้นทาง และ RPC ใช้ dynamic SQL ได้ จึงไม่ใช้การค้นชื่ออย่างเดียวรับรองว่าลบปลอดภัย
7. อ่าน project flags ได้ไม่ครบเพราะค่าบางตัวเป็น encrypted/sensitive; ไม่ถอดหรือส่งออก secrets เพื่อทำรายงานนี้ และไม่เหมาว่า flag เปิดจากการมีตาราง
8. ประวัติสแกนรวมการตรวจและงานบำรุงรักษาด้วย ไม่เท่ากับจำนวนผู้ใช้

## พื้นที่และ CAMS

`forecast_provider_snapshots` ประมาณ 120.79 MiB, aliases ประมาณ 62.17 MiB ณ catalog รอบก่อนหน้าใน session นี้ เป็นสองแหล่งหลักของพื้นที่ แต่ไม่ใช่หลักฐานว่าเลิกใช้

- snapshot read chain: `external_forecast.py` → `get_recent_cams_snapshots` → `forecast_provider_snapshots`
- snapshot write chain: protected cron `/api/cron/cams-snapshots` → `collect_openmeteo_snapshots` → sync runs/snapshots; ทำงานตาม feature flags/project guard
- grid-only writer guard มีใน deployed code แต่ค่า `CAMS_GRID_FORECAST_ENABLED` default=false และไม่พบ production project variable ชื่อนี้ในรายการที่อ่านได้ จึงไม่รับรองว่า cutover เปิดแล้ว
- SQL cron `private.prune_recent_history` ยังรวม snapshots, sync runs และ alias cleanup อยู่ ต้องรักษาการล้างข้อมูลให้ถูกกับโหมดที่ใช้จริง
- ลำดับ retirement: พิสูจน์กริดพร้อมและอ่านสถานี/พิกัดแทนได้ → เปิด reader → หยุด writer → ตรวจไม่มีการอ่านเก่า → ล้างประวัติตาม retention → ถอดตาราง/aliases ของข้อมูลชนิดนั้น
- ขนาดจาก catalog ไม่รวม WAL/free disk และไม่ได้รับรองว่า Free plan เหลือเท่าใด

## โค้ดเก่าที่ยังอ้างตารางซึ่งไม่มีอยู่แล้ว

พบ `.table(...)` ที่อ้าง `forecast_validation_snapshots`, `forecast_validation_hourly_observations`, `forecast_validation_collection_runs` แต่ไม่มี public relation เหล่านี้ใน production catalog; เป็นภาระ cleanup โค้ด/feature flag ไม่ใช่ตารางที่ต้องลบอีก

## งานที่ต้องทำก่อนลบจริง

1. เริ่มจาก report_reviews: ทดสอบ retirement ใน local โดยไม่ใช้ CASCADE; ถอด registry, preflight/reset expectations, review view และ triggers ให้ตรงกัน
2. ประเมินเครื่องเก่า: ถอด CLI/service เก่าและแก้ RPC ร่วมอย่างเจาะจง ห้ามลบ compensation ของ XP ตามไปโดยอัตโนมัติ
3. activities: ตัดสิน scope ฟีเจอร์ที่ API ยังเปิดอยู่ก่อน
4. CAMS: ทำ cutover แยก เพราะมีผลต่อกราฟ/แผนที่และคืนพื้นที่มากที่สุด
5. หากถึงขั้นลบจริง สำรองเฉพาะข้อมูลที่เกี่ยวข้องลง Mac และตรวจ restore ตามขอบเขต; ไม่สร้าง backup table/schema บน Supabase
6. ตรวจ API/SQL worker/Realtime/คะแนนและ retention หลังเปลี่ยน ไม่มีการลบใดในรอบ audit นี้
