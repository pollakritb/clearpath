## 3. Trust ผู้รายงาน: นิยามและสูตรตั้งต้น

### 3.1 หลักฐานที่นับ

ใช้ผลตรวจอิสระที่มีผู้ประเมิน/วิธีประเมิน หลักฐานอ้างอิง ขอบเขต เวลา และ revision ตรวจสอบย้อนหลังได้ เช่น การตรวจหลักฐานต้นฉบับโดยผู้ประเมินที่ไม่ใช่เจ้าของรายงาน หรือการเก็บข้อมูลภาคสนามภายใต้ protocol ที่กำหนด

ผลตรวจมี `pass`, `problem`, `unresolved` และสถานะ `superseded` สำหรับผลที่ถูกแทนที่

- `s`: เคสตรวจอิสระที่สรุปว่าการรายงานผ่านเกณฑ์
- `f`: เคสตรวจอิสระที่ยืนยันปัญหาการรายงานตามเกณฑ์
- `unresolved`: ยังสรุปไม่ได้ ไม่นับเป็นผ่านหรือไม่ผ่าน
- หนึ่งเคสที่ผูกกับรายงานเดียวกันไม่ถูกนับหลายครั้งเพราะตรวจหลายด้าน ใช้ผลสรุปเคสที่เป็นปัจจุบัน
- ภาพ/การวัด/เหตุการณ์เดียวกันที่ถูกส่งหลายรายงานต้องจัดกลุ่มก่อนนับ เพื่อไม่สมมติว่าเป็นตัวอย่างอิสระหลายชุด
- OCR เผยแพร่สำเร็จ จำนวนรายงาน คะแนนสะสม Like/Dislike อายุบัญชี และการกรอกชื่อเครื่อง ไม่เพิ่ม Trust
- OCR อ่านผิด ระบบล่ม GPS ขอใหม่ไม่ได้ หรือเครื่องคลาดเคลื่อน ไม่ใช่หลักฐานว่าผู้รายงานทำผิดโดยอัตโนมัติ ต้องระบุผลตรวจและสาเหตุให้ตรงผู้รับผิดชอบ
- ความต่างจาก Air4Thai/CAMS เป็นสัญญาณให้ตรวจเพิ่ม ไม่ใช่ผล `problem` โดยลำพัง
- หลักฐานการสอบเทียบเครื่องต้องอยู่ในประวัติเครื่อง ไม่ยกเป็นประวัติความซื่อสัตย์ของผู้ใช้

### 3.2 สูตรสำหรับทดลอง

ใช้ posterior mean แบบ Beta–Bernoulli:

`Trust = 100 × (s + 2) / (s + f + 4)`

กำหนด prior `Beta(2,2)` เพื่อไม่ให้ผลหนึ่งเคสทำให้เป็น 0 หรือ 100 ทันที ค่า prior นี้เป็นการตัดสินใจออกแบบสำหรับทดลอง ไม่ใช่ค่าที่งานวิจัยรับรองว่าเหมาะกับ ClearPath ต้องทดสอบ sensitivity กับ Beta(1,1), Beta(2,2) และข้อมูลจริงก่อนเปิดใช้

| ผ่าน | พบปัญหา | Trust ตั้งต้น | การแสดงผล                                  |
| ---: | ------: | ------------: | ------------------------------------------ |
|    0 |       0 |          null | ยังไม่มีผลตรวจอิสระ ไม่แสดง 50/100         |
|    1 |       0 |          60.0 | ตรวจแล้ว 1 เคส ยังมีข้อมูลน้อย             |
|   18 |       2 |          83.3 | ตรวจแล้ว 20 เคส พร้อมรายละเอียดผล          |
|    0 |       3 |          28.6 | ตรวจแล้ว 3 เคส พร้อมสาเหตุและสิทธิ์ขอทบทวน |

แสดงจำนวนเคสและช่วงเวลาที่ตรวจควบคู่คะแนนเสมอ ไม่ตั้งป้าย “เชื่อถือได้สูง” หรือ cutoff ผ่าน/ไม่ผ่านจากตัวเลขที่ยังไม่มีการประเมินรองรับ ไม่ลดคะแนนเพียงเพราะไม่ได้ใช้งาน เมื่อแก้ผลตรวจให้คำนวณใหม่จาก revision ปัจจุบัน ไม่แก้เลข Trust ด้วยมือ

หลักทางสถิติ: [University of Toronto — Beta/Bernoulli update](https://www.teach.cs.toronto.edu/~csc311notes/probabilistic_modelling/probabilistic_modeling_intro.html) รองรับวิธีอัปเดตพารามิเตอร์ แต่ไม่รับรองเกณฑ์ตรวจ ความเป็นอิสระของข้อมูล หรือ prior ที่เลือกสำหรับผลิตภัณฑ์นี้

### 3.3 ตำแหน่งที่แสดง

- โปรไฟล์: คะแนนสะสม/ยศ ตามด้วย Trust ผู้รายงานและจำนวนเคสตรวจ แยกเป็นคนละข้อมูล
- หมุดรายงานบุคคลที่ยินยอมแสดงโปรไฟล์: ชื่อ/รูป ตามด้วย Trust ผู้รายงาน; คะแนนหลักฐานอยู่ในรายละเอียดรายงาน
- หมุดคลัสเตอร์: ไม่เฉลี่ย Trust ของคนทั้งหมดเป็นค่าเดียว เปิดดูเป็นรายคน
- รายงานไม่เปิดเผยตัวตน: ไม่แสดงคะแนนหรือสถิติส่วนบุคคลที่ใช้เชื่อมหลายรายงานกลับมาหาบัญชีได้
- สถานี Air4Thai และกริด CAMS: แสดงแหล่งข้อมูล/เวลา ไม่ใช้ Trust ของผู้รายงานบุคคล
- มีคะแนนปัจจุบันหนึ่งค่าต่อบัญชี ส่วน snapshot ขณะส่งและเหตุผลการตัดสินเก็บสำหรับ audit พร้อม version; ไม่เรียก snapshot ว่า Trust รายงาน

### 3.4 ผลต่อการใช้ค่าฝุ่น

ในการเปิด policy bundle ใหม่ครั้งเดียว ให้เลิกใช้ Trust รายงานสูตรเดิมเป็นเงื่อนไข gap-fill แล้วใช้หลักฐานรายงาน ความสด ตำแหน่ง บริบท และการยืนยันจากแหล่งวัดอิสระตามเกณฑ์ที่ประเมินแล้ว

Trust ผู้รายงานใช้แสดงประวัติและจัดลำดับคิวตรวจในรุ่นแรก ไม่ใช้คูณ PM2.5 ไม่ทำให้ข้ามเกณฑ์หลักฐาน ไม่เพิ่ม XP ไม่ใช้ตัดสินอันดับเสมอกัน และไม่ตั้งขั้นต่ำที่ทำให้ผู้ใช้ใหม่หมดสิทธิ์เพียงเพราะยังไม่มีผลตรวจ

รายงานที่ยืนยันแล้วว่าหลักฐานใช้ไม่ได้ถูกกันออกตามผลตรวจของรายงานนั้น ไม่เหมารวมทุกรายงานของบัญชีโดยอัตโนมัติ Place IDW วง 2 กม. คง distance-only weighting ตามกติกาปัจจุบัน

## 4. แผนงานทั้งหมดและเกณฑ์ส่งมอบ

### P0 — ทำบัญชีสถานะจริงและเก็บ baseline

- `BASE-01`: ทำรายการฟีเจอร์แยก deployed/enabled/local-only/retired และเจ้าของงาน
- `BASE-02`: บันทึก commit, schema/migration versions, release pointers, flags ที่ไม่เป็นความลับ, scheduler และ provider generation
- `BASE-03`: บันทึกคะแนน/ยศเดิม จำนวนบัญชีและรายงานเพื่อเทียบก่อน–หลัง โดยไม่คัดลอก raw GPS/keys ลงเอกสารสาธารณะ
- `BASE-04`: แยก release branch และ refactor branch พร้อมตรวจไฟล์ค้าง ไม่ใช้การ stage ทั้ง workspace
- ผ่านเมื่อสถานะไม่อาศัยชื่อหน้าจอหรือ checklist เก่า และมี baseline/rollback ที่ตรวจซ้ำได้

### P1 — แก้ CAMS และคุณภาพข้อมูลสถานี

- `DATA-01`: ตรวจงาน collector, cron, batch limits, upstream horizon และ ready generation ที่ใช้จริง
- `DATA-02`: คำนวณจำนวนเวลาที่เป็นอนาคตจากเวลาปัจจุบัน แสดงช่วงเริ่ม–สิ้นสุดจริงและอายุชุดข้อมูล
- `DATA-03`: เก็บ/ต่ออายุให้ครอบคลุมอนาคตสูงสุดที่ provider ให้ ห้ามเติมค่าหรือเลื่อน timestamp เพื่ออ้างว่าครบ 120 ชั่วโมง
- `DATA-04`: หาก provider ให้ไม่ครบห้าวัน ให้ UI บอกช่วงที่มีจริง; ไม่ถือว่าครบข้อกำหนดห้าวันจน upstream และ collector ทำได้จริง
- `DATA-05`: station/area forecast และ grid ต้องตรวจ generation/run provenance และ valid times ที่เข้ากันได้ ระบุแหล่งต่างชุดถ้าจำเป็น
- `DATA-06`: ติดตามสถานีหมดอายุ แยกต้นทางไม่มีข้อมูลออกจาก collector ล้มเหลว พร้อมแจ้งเตือนงานซิงก์ผิดปกติ
- ผ่านเมื่อ boundary เวลาไทย/UTC, ข้ามวัน, งานเก็บขาดช่วง, generation ไม่ครบ, stale และ retry มี tests; ไม่มีข้อความรับรองระยะพยากรณ์เกินข้อมูลจริง

### P2 — พัฒนา Reporter Trust และเส้นทางหลักฐาน

- `TRUST-01`: ล็อก rubric ว่าอะไรตรวจผ่าน/พบปัญหา/ยังสรุปไม่ได้ และอะไรเป็นปัญหาเครื่องหรือระบบ
- `TRUST-02`: พัฒนาฟังก์ชันคำนวณ pure พร้อม version, null state, จำนวนเคส, เวลา และเหตุผล
- `TRUST-03`: ใช้ ledger ผลตรวจเดิมเป็นหลัก เพิ่ม projection/snapshot เท่าที่จำเป็น ไม่สร้างคะแนนย้อนหลังจาก OCR-approved
- `TRUST-04`: นำเข้าผลตรวจผ่าน server process พร้อม provenance, dedup, revision, recomputation และ replay safety; Admin dashboard อ่านได้เท่านั้น
- `TRUST-05`: ปรับ API และ TS/Pydantic contracts ให้แยก reporter Trust, report evidence และ device status; deprecate legacy fields อย่างมี version
- `TRUST-06`: ทดสอบ prior sensitivity, ความไม่สมดุลของการสุ่มตรวจ, เคสที่สัมพันธ์กัน, การแก้ผล และผู้ใช้ใหม่ก่อนเลือกสูตรเปิดใช้
- `TRUST-07`: มีวิธีขอทบทวนผลตรวจพร้อมหลักฐาน โดยไม่เปิดปุ่ม Admin เพิ่ม/ลดคะแนนตามอำเภอใจ
- ผ่านเมื่อผลทุกค่าคำนวณย้อนกลับได้ ไม่มี double count ไม่มีการใช้ popularity และไม่เปิดข้อมูลนิรนามย้อนหาบัญชี

### P3 — คะแนนสะสม อันดับ และ gap-fill เปิดเป็น policy bundle

- `SCORE-01`: เก็บคะแนน/ยศเดิม เริ่มโบนัสใหม่ที่ T0 เท่านั้น; ไม่สร้างโบนัสย้อนหลัง
- `SCORE-02`: คง +10 รายงาน, +5 รายงานแรกของวัน, +5 ช่วยคำขอหรือภารกิจ และ +20 ครบห้าวัน ตามเพดาน/ช่วงรอที่ตกลง
- `SCORE-03`: อันดับเดือนปฏิทินเวลาไทยและคะแนนทั้งหมด; คะแนนเท่ากันอันดับร่วม ไม่ใช้ Trust ตัดสิน
- `SCORE-04`: ทดสอบ ledger/โบนัส/compensation พร้อมกันหลาย connection บน staging; retry/replay ต้องไม่เพิ่มรางวัลซ้ำ
- `GAP-01`: ทดสอบนโยบายหลักฐานและ corroboration ใหม่กับชุดอิสระก่อนเปลี่ยนสูตรเดิมจริง ไม่มีทางลัดเพราะเครื่องสอบเทียบหรือ Trust สูง
- `GAP-02`: คนใหม่ไม่มี Trust ยังส่งและรับคะแนนได้ตามกติกา; gap-fill ต้องผ่านหลักฐานและแหล่งวัดอิสระเช่นเดียวกันทุกคน
- `MISSION-01`: รุ่นแรกใช้พื้นที่นำร่องตามที่มีจริง ไม่อ้างว่าภารกิจครอบคลุมทั่วประเทศ
- ผ่านเมื่อข้อสอบก่อน/หลัง T0 ข้ามเดือน ข้ามสัปดาห์ rerun งานช้า ถอนผลตรวจ และ rollback ไม่ทำคะแนนเก่าหายหรือเปลี่ยนเดือนของเหตุการณ์

### P4 — คำขอ พื้นที่รับคำขอ และโหวต

- `REQUEST-01`: บันทึกพื้นที่รับคำขอได้ไม่เกินสองจุดต่อบัญชี พิกัดเป็นส่วนตัว และทดสอบการแก้/พักรับ/ลบ
- `REQUEST-02`: ห้าคำขอที่มีรัศมีครอบคลุมรายงานเดียวกันต้องได้ผลครบทั้งห้าราย ไม่ต้องกดรับช่วยก่อน และโบนัสบริการมีครั้งเดียวต่อรายงาน
- `REQUEST-03`: ทดสอบตรงขอบรัศมี วงซ้อน คำขอของตัวเอง หมดอายุ ยกเลิก รายงานเก่าที่ไม่อยู่ในหมุดสด และ retry outbox
- `VOTE-01`: เริ่มที่ 500 ม. ชั่วคราวตามคำสั่งเดิม บันทึกว่าเป็น product policy ไม่ใช่ระยะที่งานวิจัยรับรอง
- `VOTE-02`: คำนวณ haversine บน server จากพิกัดจริงที่ไม่ส่งกลับ public; ระยะ + accuracy ผู้โหวต + accuracy จุดวัด ≤500 ม.; คร่อมขอบให้ขอ fix ใหม่
- `VOTE-03`: GPS อายุไม่เกิน 60 วินาที รายงานไม่เกินสามชั่วโมง ไม่โหวตตนเอง หนึ่งปฏิกิริยาต่อคน เปลี่ยน/ถอนได้; Dislike ต้องเลือกเหตุผล
- `VOTE-04`: โหวตและ Comment ไม่เปลี่ยน Trust/XP; ลดการปั๊มด้วย authentication, rate limit, uniqueness และ anomaly logs โดยไม่อ้างว่า browser GPS ป้องกัน spoof ได้สมบูรณ์
- ผ่านเมื่อ hosted concurrency, privacy และ fanout/notification dedup ผ่านทั้ง fixtures และเคสจริงที่ได้รับความยินยอม

### P5 — UX/UI และอุปกรณ์จริง

- `UX-01`: ใช้ Impeccable, UI/UX Pro Max, Web Design Guidelines ต่อจากอัตลักษณ์เดิม; เฟรมเดียวไม่เกิน 430 px ไม่มี desktop layout แยก
- `UX-02`: โปรไฟล์แยกคะแนน/ยศ, Trust ผู้รายงาน, คะแนนหลักฐาน และสถานะเครื่อง ชื่อ/คำอธิบายไม่ใช้สลับกัน
- `UX-03`: แผนที่ค้นหา → เลื่อนแผนที่ใต้หมุดกลาง → ยืนยัน; ย้อนหลัง/พยากรณ์แยกปุ่มและกลับสถานีได้; พยากรณ์สถานีไม่เปิด grid
- `UX-04`: ทุก flow มี loading/empty/error/retry, target ที่กดได้, focus, screen-reader labels และข้อความยาวไม่ล้น
- `DEVICE-01`: ทดสอบ iPhone และ Android จริง: กล้อง ปฏิเสธ/ยกเลิกสิทธิ์ GPS คลาดเคลื่อน คีย์บอร์ด orientation และกลับจาก background
- `DEVICE-02`: ทดสอบ VoiceOver/TalkBack, ขยายข้อความ และ reduced motion โดยคนใช้งานจริง
- ผ่านเมื่อมีรายการอุปกรณ์/OS/เบราว์เซอร์จริงพร้อมผลและภาพ ไม่ใช้ mobile emulation แทนหลักฐานทั้งหมด

### P6 — LINE, inbox และ notification delivery

- `NOTIFY-01`: ทดสอบบัญชีจริงที่ยินยอม: เชื่อมบัญชีผิด/ถูก unlink/หมดอายุ code/consent/quiet hours
- `NOTIFY-02`: ทดสอบส่งจริงขณะปิดเว็บ รายงานตอบหลายคำขอ และ inbox link เปิดรายงานเก่าหรือแจ้งกรณีหลักฐานหมด retention อย่างเหมาะสม
- `NOTIFY-03`: ทดสอบ provider timeout, retry, duplicate delivery และ replay; หนึ่งเหตุการณ์ไม่เพิ่ม inbox/outbox ซ้ำ
- `NOTIFY-04`: ตรวจ scheduler/outbox health พร้อม dead-letter/recovery และผู้รับผิดชอบ
- Web Push ถือเป็นขอบเขตเสริมจนมี keys/consent และผลส่งจริง; ไม่อ้างว่าเปิดพร้อม LINE ถ้ายังไม่มีหลักฐาน
- ผ่านเมื่อมี delivery receipts/logs ที่ไม่เปิด raw GPS/keys และไม่มีการส่งทดสอบไปยังบุคคลที่ไม่ยินยอม

### P7 — บัญชี ความเป็นส่วนตัว ความปลอดภัย และการกู้คืน

- `PRIV-01`: ออกแบบ export/delete account แบบผู้ใช้ยืนยันตัวตนซ้ำ อธิบาย retention ของ ledger/audit ที่ต้องเก็บและการลบ/ปิดบัง public identity
- `PRIV-02`: ทดสอบ private photo bucket, signed URL expiry, owner access, public obfuscation และการเชื่อม anonymous reports ข้ามเวลา
- `SEC-01`: ทดสอบ object authorization/RLS, rate limits, private-location isolation, secret exposure และ security review ขอบเขตจริง
- `OPS-01`: ซ้อม backup/restore ในโปรเจกต์แยก พร้อมตรวจรายงาน คะแนน คำขอ และ references หลัง restore; ไม่ทำ destructive drill บน production
- `OPS-02`: ทดสอบโหลดหลาย connection และกำหนด alert ที่เกิดจาก failure จริง เช่น collector lag, stale data, OCR error และ outbox backlog
- `OPS-03`: ระบุ owner/ผู้สำรอง เหตุขัดข้อง rollback และช่องทางสื่อสาร พร้อมให้เจ้าของตรวจ license/privacy/health copy
- ผ่านเมื่อมีหลักฐานซ้อมจริงและผู้รับผิดชอบ ไม่ใช่เพียงมีไฟล์ runbook

### P8 — รวม refactor และทำเอกสารให้ตรง production

- `CLEAN-01`: ตรวจ persistence split, CSS consolidation, map behavior extraction และการถอด legacy forecast pipeline เป็น release แยก
- `CLEAN-02`: เทียบ retained API/contracts/ผลคำนวณ/SQL query counts และ visual regression ก่อน–หลัง; ไม่ลด tests เพื่อให้ผ่าน
- `DOC-01`: สร้างรายการฟีเจอร์ปัจจุบันและ matrix deployed/enabled/retired; ทำเครื่องหมายแผนเก่าเป็นประวัติแทนการลบหลักฐาน
- `DOC-02`: อัปเดต README, architecture, ERD/data dictionary, Trust policy,คะแนน และ runbooks ให้ใช้ version เดียวกัน
- ผ่านเมื่อโค้ดที่อธิบายในเอกสารตรงกับ commit ที่ deploy และไม่มีการ activate pipeline เก่าจาก flag โดยไม่ตั้งใจ

### P9 — Pilot, rollout และตรวจหลังเปิดใช้

- `RELEASE-01`: baseline/backup + additive migrations บน staging; ตรวจ RLS/permissions/indexes และทาง rollback
- `RELEASE-02`: deploy โค้ดที่รองรับรุ่นเก่าและใหม่โดยยังไม่สลับ pointer ตรวจ flags ทั้งทุก instance และ worker
- `RELEASE-03`: dry-run evaluation/reconciliation เทียบผลเดิม เลือก Trust prior/rubric และ gap-fill threshold จากหลักฐานจริง พร้อมเก็บ artifact
- `RELEASE-04`: เปิดกลุ่ม pilot ที่ยินยอม ตรวจ task success, ข้อมูลผิดพลาด, Trust explanations, notification usefulness และความเป็นธรรมต่อคนใหม่
- `RELEASE-05`: เปลี่ยน policy bundle ครั้งเดียวที่ T0 เมื่อ gates ผ่าน ตรวจคะแนน/อันดับ/Trust/gap-fill/โหวตตรง version เดียวกัน
- `RELEASE-06`: rollback ด้วย pointer/flags และ version-aware reconciliation ไม่ลบ ledger/ผลตรวจหรือทำรายงานที่เผยแพร่แล้วสูญหาย
- `RELEASE-07`: ตรวจ production commit, health/readiness, collector freshness, auth protection, signed images และ outbox ต่อเนื่องตามรอบงานจริง
- ผ่านเมื่อ baseline เทียบได้ end-to-end และเจ้าของยอมรับผล pilot; ห้ามใช้เพียง deployment สีเขียวแทนการจบงานทั้งหมด

## 5. ลำดับและงานที่ทำคู่กันได้

ลำดับหลัก: P0 → P1 → P2/P3/P4 → P5/P6/P7 → P8 → P9

งาน field evidence, เตรียมอุปกรณ์จริง, บัญชี LINE และหลักฐาน license เริ่มเตรียมได้ตั้งแต่ P0 เพราะเป็น dependency ที่โค้ดแทนไม่ได้ Refactor มี branch ของตนเอง ทำแยกได้ แต่ไม่รวม release โดยไม่มี regression evidence

ทุก task ใช้สถานะ Not started / In progress / Implemented / Verified local / Verified staging / Enabled production / Accepted พร้อมลิงก์หลักฐาน ไม่เรียก Implemented ว่าเปิดใช้งานแล้ว

## 6. Definition of done

- User Trust ผูกบัญชีเดียวและอธิบายการคำนวณ/ผลตรวจได้ ไม่ปะปน XP/Like/Report evidence
- ไม่มีผลตรวจไม่แสดง Trust 0 หรือ 50 แทนข้อมูลที่ไม่มี
- คะแนนและยศเดิมคงอยู่ ไม่มีโบนัสซ้ำหรือ backfill ที่ไม่ได้อนุญาต
- คำขอห้าคนได้ผลครบและไม่มีข้อมูลตำแหน่งส่วนตัวรั่ว
- CAMS แสดงระยะอนาคตจริง และไม่รับรองครบห้าวันเมื่อ provider ไม่ได้ให้มา
- ผ่าน frontend/backend/unit/contract/database/browser tests ที่เกี่ยวข้อง พร้อมหลักฐาน real-device และ LINE จริง
- ไม่มี RLS/authorization/privacy regression; backup restore และ rollout/rollback ซ้อมแล้ว
- Code version, schema, policy, worker, UI และเอกสารตรงกัน
- สิ่งที่ยังรอ external evidence ระบุเป็น pending อย่างชัดเจน ไม่สร้างข้อมูลปลอมให้ผ่าน gate

การส่งแผนนี้ไม่อนุมัติการเปิด feature flags, เปลี่ยน database, ส่งข้อความจริง หรือ deploy เพิ่มโดยอัตโนมัติ เป็นการจัดทำแผนตามคำขอครั้งนี้
