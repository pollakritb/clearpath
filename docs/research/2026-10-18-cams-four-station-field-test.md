## ข้อจำกัดและสถานะความแม่นยำ

**ยังคำนวณ MAE/Bias หรือกล่าวว่าพยากรณ์ “แม่นกี่เปอร์เซ็นต์” ไม่ได้** Air4Thai ระบุว่ากราฟรายชั่วโมงเป็นค่าเฉลี่ย 1 ชั่วโมง ต่างจากค่าหัวข้อหลักที่เป็นค่าเฉลี่ย 24 ชั่วโมง แต่ endpoint ประวัติ `type=hr` ไม่ได้ยืนยันว่า `DATETIMEDATA` เป็นเวลาเริ่มหรือสิ้นสุดช่วงเฉลี่ย `[start,end)` ใด จึงยังไม่สามารถรับรองว่าตรงกับ `valid_at` ของ CAMS หรือไม่ ไฟล์ข้อมูลกำหนด `scorable:false` ให้ทุกคู่และไม่เก็บผลต่าง/MAE เพื่อป้องกันการอ้างผลผิดเวลา นอกจากนี้ค่า PM2.5 รายชั่วโมงของ Open-Meteo เป็นค่าที่ API ให้ ณ เวลาที่ระบุ ขณะที่ CAMS Global มีความละเอียดแบบจำลองดั้งเดิมราว 0.4°/45 กม. และรอบ native ทุก 3 ชั่วโมง; จุดศูนย์กลาง grid ที่ใกล้สถานี 3–6 กม. จึงไม่พิสูจน์ว่าแบบจำลองแทนสภาพเฉพาะถนนได้

แหล่งนิยาม: [คำอธิบายค่าเฉลี่ย 1/24 ชั่วโมงจากกรมควบคุมมลพิษ](https://epo08.pcd.go.th/th/news/detail/180206), [Open-Meteo Air Quality API: grid-cell centre และ CAMS Global resolution](https://open-meteo.com/en/docs/air-quality-api) และ [คู่มือการตรวจภาคสนามของ ClearPath](../forecast-field-validation.md) ข้อมูล Air4Thai ถูกเก็บเฉพาะในไฟล์ local/gitignored จนกว่าจะทบทวนเงื่อนไขการนำข้อมูลไปเผยแพร่

## วิธีทำซ้ำและเงื่อนไขก่อนให้คะแนน

รันจาก root ของ repo ด้วย `.venv/Scripts/python -m scripts.cams_four_station_trial` สคริปต์ตรวจ project ref ให้ตรง ClearPath ก่อนอ่าน, จำกัด 4 station ID ข้างต้น, อ่านเฉพาะ CAMS `openmeteo_cams` ย้อนหลังไม่เกิน 7 วัน, ดึง Air4Thai history แบบ `type=hr`, คำนวณระยะ Haversine และเขียน JSON ใหม่ใต้ `.forecast-validation/` ไม่เขียน Supabase หรือ API พยากรณ์

ขั้นถัดไปต้องได้เอกสารหรือการยืนยันจาก Air4Thai/กรมควบคุมมลพิษว่า timestamp ของ `type=hr` หมายถึงช่วงเฉลี่ยชั่วโมงใดและสิทธิ์ใช้งานข้อมูล จากนั้นจึงจับคู่ด้วย `window_end_at=valid_at` เฉพาะพยากรณ์ที่ดึงก่อนเวลา valid แยกรายสถานีและ lead time, รายงานจำนวนชั่วโมงไม่ซ้ำ/ข้อมูลขาด/MAE/signed bias รวมถึงทดสอบช่วงฝุ่นสูงบนข้อมูลหลายวันหรือหลายสัปดาห์ ไม่ใช้ผลการทดลอง 4 สถานีรอบเดียวปรับค่าที่ผู้ใช้เห็น

\* “คู่เวลาเบื้องต้น” หมายถึง timestamp ที่ตรงกันตาม **สมมติฐานที่ยังไม่ยืนยัน** เท่านั้น ไม่ใช่คู่ข้อมูลสำหรับประเมินความแม่นยำ

## ชุดทดลองอิสระ 4 สถานี (เริ่ม 18 ต.ค. 2569)

ตามข้อกำหนดให้แยกจาก Production มีสคริปต์ [collect_independent_cams_trial.py](../../scripts/collect_independent_cams_trial.py) ซึ่งใช้พิกัดสถานี 4 แห่งที่บันทึกไว้ข้างต้น **เรียก Open-Meteo/CAMS Global และ Air4Thai history โดยตรง** ไม่อ่านหรือเขียน Supabase, ไม่ใช้ snapshot ของ Production, และไม่เปลี่ยนพยากรณ์ที่แสดงในเว็บ ไฟล์แต่ละรอบอยู่ใน `.forecast-validation/independent-four-station/` ซึ่งถูก `gitignore` ไว้ ไม่มี secret ในไฟล์ รอบที่ซ้ำในช่วง UTC 6 ชั่วโมงเดียวกันจะไม่เขียนทับไฟล์เดิม

รอบอิสระแรกเก็บเวลา **18 ต.ค. 2569 12:00 UTC slot**: [ไฟล์ JSON](../../.forecast-validation/independent-four-station/trial-20261018T120000Z.json), ขนาด **81,120 ไบต์**, SHA-256 `7ac6f491f5e4dba80f3999ad1050288b85c1163ebc34d470b29a2b375f390c20` ได้ข้อมูลพยากรณ์อนาคตครบ **24 ชั่วโมง × 4 สถานี = 96 จุด** ไฟล์บันทึกเวลาที่ดึง, เวลาที่พยากรณ์ใช้ได้, พิกัดสถานี, ศูนย์กลาง grid, ระยะทาง และป้ายค่ารายชั่วโมง Air4Thai แยกต่างหาก ไม่มี MAE/Bias เพราะนิยามช่วงเวลา Air4Thai ยังไม่ยืนยัน

เพื่อให้ครบ **7 วันต่อเนื่อง** ตั้ง Windows Scheduled Task ชื่อ `ClearPath-CAMS-Four-Station-Trial` บนเครื่องนี้แล้ว โดยใช้ [ตัวรัน](../../scripts/run_independent_cams_trial.ps1) ภายใต้บัญชีผู้ใช้ปกติ (`Interactive`, ไม่ใช้สิทธิ์ Admin), เริ่มรอบถัดไป **19 ต.ค. 2569 เวลา 01:00 น. ไทย** และทำซ้ำทุก 6 ชั่วโมง เป้าหมายรวมกับรอบแรกคือ **28 UTC slots** ตั้งแต่ 18 ต.ค. 12:00 UTC ถึงก่อน 25 ต.ค. 12:00 UTC สคริปต์มี stop window อิสระอีกชั้นหนึ่ง จึงไม่ส่งคำขอหลังครบ 7 วัน Task ถูกสั่งรันทดสอบแล้ว `LastTaskResult=0`; เมื่อรอบเดิมมีไฟล์แล้วจะไม่เขียนทับ

ตรวจสถานะด้วย `Get-ScheduledTaskInfo -TaskName ClearPath-CAMS-Four-Station-Trial` และดูไฟล์/บันทึกที่ `.forecast-validation/independent-four-station/` (รวม `collector-run.log`) เครื่องต้องเปิด, ต่ออินเทอร์เน็ต และบัญชีนี้ยังลงชื่อเข้าใช้; การปิดเครื่องหรือออกจากระบบอาจทำให้บางรอบขาด แม้ตั้ง `StartWhenAvailable` และ retry ไว้ **ยังไม่มีหลักฐานว่าครบ 7 วันจนกว่าจะตรวจไฟล์ทั้ง 28 รอบหลังสิ้นสุด** ไม่ใช้ cron ของ Production หรือ deploy Vercel และห้ามย้ายไฟล์หลักฐานดิบไป Git หรือ Production database
